# 05. 技術メモ（TDD：技術設計ドキュメント）

> ソロ・初心者前提の軽量版。**最初から完璧に設計しない。** コードと一緒に育てる。
> ただし「セーブデータ形式」と「モデル層/ビュー層の分離」だけは早めに方針を固める（後から直すのが最も高くつくため）。

---

## 1. 環境（実際に導入した構成・2026年9月時点）

| 項目 | 決定・実測値 |
|---|---|
| エンジン | Godot **4.7.2**（.NET版／`mono`付き実行ファイル） |
| .NET SDK | **9.0.302**（`dotnet --version` で確認済み） |
| プロジェクトの TargetFramework | **`net8.0`**（Godot側プロジェクトが `net8.0` を要求するため、`GuildManager.Core.csproj` も明示的に `net8.0` に合わせてある。.NET 9 SDK は下位互換でこれをビルドできる） |
| 言語 | C# |
| 対象OS | PC（Windows / macOS / Linux） |
| Web 書き出し | **非対応**（Godot の C# は HTML5 出力不可）。Web 版が必要なら GDScript 移植か別方針が必要 |
| バージョン管理 | Git + GitHub。Phase 0 で導入済み |
| エディタ | Visual Studio / Rider / VS Code のいずれか |

> **経緯メモ:** 当初「.NET 8 SDK」を前提に案内していたが、実際にインストールした Godot 4.7.2 は .NET 9 系のSDKを要求した（`dotnet new classlib` のデフォルトも `net9.0` になった）。一方Godot側の生成プロジェクトは `net8.0` のままだったため、`GuildManager.Core.csproj` の `<TargetFramework>` を `net9.0` → `net8.0` に書き換えて揃えた。**「.NET SDKのバージョン」と「プロジェクトのTargetFramework」は別物**であり、新しいSDKで古いTargetFrameworkのプロジェクトをビルドすることは通常問題ない。今後 `dotnet new` で追加のプロジェクトを作る際は、生成された `.csproj` の `TargetFramework` が `net8.0` になっているか毎回確認すること。

## 2. プロジェクト構成（モデル層とビュー層の分離）

コンセプトの根幹である「純 C# ロジックと Godot UI の分離」を、プロジェクト構成で強制する。

**実際のフォルダ名について:** Godotの新規プロジェクト作成時、プロジェクト名に `GuildManager.Godot` と入力したが、Godotがフォルダ名として自動的に `guild-manager.godot`（小文字・ハイフン区切り）に変換した。`.csproj` ファイル自体は `GuildManager.Godot.csproj` の名前で作られている。フォルダ名とcsproj名が異なる点は動作上問題ないが、紛らわしいので以下は実際のフォルダ名で記載する。

```
GuildManager/                          ← リポジトリルート（Git管理）
├── docs/                              ← 企画・仕様書一式（01〜06・README）
├── .gitignore
│
├── guild-manager.godot/                ← Godot プロジェクト（ビュー層）実フォルダ名
│   ├── project.godot
│   ├── GuildManager.Godot.csproj       ← Core への参照を追加済み
│   ├── GuildManager.Godot.sln
│   ├── *.tscn                          ← シーン（main_dashboard・dungeon_panel・research_panel 等。プロジェクト直下に配置）
│   ├── scripts/                        ← Godot Node に貼る C#（表示・入力のみ。MainDashboard・各ポップアップ）
│   │   └── UI/                         ← 中央ペインの各タブ（DungeonPanel・ResearchPanel・FacilityPanel・PartyFormationPanel）
│   └── addons/godot_ai/                ← MCP連携プラグイン（エディタ／ゲーム実行時の連携用）
│
├── GuildManager.Core/                  ← 純 C# クラスライブラリ（.csproj）Godot 非依存
│   ├── GuildManager.Core.csproj        ← TargetFramework は net8.0 に統一
│   ├── Models/    Adventurer, Party, GameState, DungeonField, FloorBoss, ActiveDungeonMission,
│   │              ResearchDefinition, SaveData ...（稼働中）
│   ├── Systems/   週次決算 WeekProcessingSystem・AgingSystem・SatisfactionSystem・EconomySystem 等に加え、
│   │              大迷宮系 DungeonExpeditionSystem・DungeonTraversalResolver・ScoutingResolver・
│   │              DungeonResolver・GatheringResolver、研究室 ResearchSystem、SaveLoadService ...（稼働中）
│   ├── Balance/   バランス値の読み込み（docs/04_バランス表/*.csv → static readonly、→ §3）（稼働中）
│   ├── Data/      初期データ（SampleData：初期冒険者・5フィールドと階層ボスの定義）（稼働中）
│   └── Rng/       決定論的乱数（IRng・SeededRng、下記）（稼働中）
│
└── GuildManager.Core.Tests/            ← xUnit テスト（Core のみを対象。→ §7）
```

- **原則:** `GuildManager.Core` は `using Godot;` を一切書かない。これによりバランス調整・ロジックのユニットテストが Godot 抜きで可能になる。
- ビュー層は Core の `GameState` を読んで描画し、ボタン入力を Core のシステム呼び出しに変換するだけ。

## 3. バランス値の外部化（項目58で実装済み。→ 03 §10.1）

**数値をコードに直書きしない。** `docs/04_バランス表/` 配下のCSV群を正本とし、実行時に読み込む。

- 利点：再ビルドせずに調整でき、遊びながらの試行錯誤が速い。
- 実装：CSVは実行ファイルの隣（`.csproj` の `Content`/`CopyToOutputDirectory` で
  自動配置）に置き、`GuildManager.Core/Balance/BalanceData.cs` が読み込む。
  各 `Balance/` クラスの `static readonly` フィールドがここから値を取得する。
  CSVが読めない・キーが無い・パースできない場合はいずれも例外にし、コード側に
  デフォルト値のフォールバックは持たない（値の二重管理を避けるため）。
- 旧 `04_バランス表.xlsx`（v1.0〜v1.1時点の作成後、実コードの改訂に追従できず
  乖離していた）は廃止した。

## 4. セーブ / ロード（早めに方針だけ固める）

- **形式:** `GameState` を **JSON シリアライズ**（`System.Text.Json`）。人間可読でデバッグしやすい。
- **保存先:** Godot の `user://` パス（OS ごとの適切なユーザ領域）。
- **タイミング:** 週送り完了ごとにオートセーブ（＋手動保存ボタン）。
- **スロット:** 単一スロット（`savegame.json`、常に上書き保存。→ `SaveLoadService`）。複数スロットは post-MVP。
- **設計上の注意:** `GameState` は最初からシリアライズ可能に作る（循環参照を避け、参照は ID で持つ）。後付けは苦しい。

## 5. 乱数（決定性・再現性）

- **注入可能な RNG** を Core に持たせる（`IRng` インターフェース → 実装差し替え可能）。
- **シードをセーブに保存**し、乱数ストリームを1本に統一。これでバグ再現・リプレイ・テストが安定する。
- Godot の `RandomNumberGenerator` ではなく Core 側の RNG を正とする（ロジックが Godot 非依存でいられる）。

## 6. UI スケーリング（v1.1 §9 の実装方針）

- `project.godot` の Display > Window:
  - `content_scale_mode = canvas_items`
  - `content_scale_aspect = expand`
  - 基準サイズ 1920×1080
- 各ペインは固定 px 直書きではなく **Anchor ＋ Container**（`HBoxContainer` / `MarginContainer` 等）で組み、仕様書の px 値は「基準時の目安」として `custom_minimum_size` 等に反映。

## 7. テスト方針（軽量）

- Core はプレーン C# なので、`xUnit` 等でユニットテスト可能。
- 最優先でテストしたいのは**壊れると分かりにくい計算系**：QuestResolver（比率・致死判定の境界）、AgingSystem（稼働週数・加齢ロール・満期引退）、EconomySystem（破産判定の4週カウント）。
- UI はテストしない（手動確認で十分）。
