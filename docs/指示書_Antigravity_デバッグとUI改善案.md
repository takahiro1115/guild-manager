## 1. 絶対に守ること

1. **ユーザーの実セーブを壊さない。**
   実セーブは `%APPDATA%\Godot\app_userdata\GuildManager.Godot\savegame.json`（同じフォルダに `profile.json` も）。
   このゲームは**月を進めるたびに自動で保存する**ので、元のプロジェクトを一度起動して「次の月へ」を押すだけで上書きされる。
   次のことは**しない**：
   - 元のプロジェクト（リポジトリの `guild-manager.godot`）を Godot エディタで開いて ▶（F5／F6）で実行する
   - 元のプロジェクトを開いているエディタに対して MCP の `project_run` を呼ぶ
   - `godot --path guild-manager.godot` のように、元のプロジェクトをコマンドで起動する
2. **ゲームを動かすのは、必ず §3 のサンドボックス（コピー）だけ。** 起動の前に毎回、相手がサンドボックスであることを確かめる（§3.5）。
3. 実セーブとそのフォルダは**読むだけ**。状態を再現したいときは、コピーをサンドボックス側へ置く（§3.6）。
4. git は操作しない（commit・push・ブランチの切り替え・reset・stash・clean・checkout によるファイルの巻き戻し）。ユーザーが頼んだときだけ。
5. `dotnet format` は使わない（既存コードが整形規則にそろっておらず、無関係な差分が大量に出る）。
   NuGet パッケージなど新しい依存を足さない。`guild-manager.godot/addons/godot_ai/`（MCP のプラグイン）は変えない。
6. リポジトリに大きなファイルや作業用の一時ファイルを置かない（リポジトリはクラウドで同期されている）。
   一時ファイルはサンドボックス側か、その隣の作業フォルダに置く。
7. 頼まれた範囲の外の作業をしない。範囲の外で気づいたことは報告書の「範囲外で気づいたこと」に一行で書く。

## 3. 動かす環境（サンドボックス）の準備

ゲームを動かす作業は、すべてここで作るコピーで行う。コピーはプロジェクト名を変えてあるので、保存先が
`%APPDATA%\Godot\app_userdata\GuildManager.Sandbox\` に分かれ、実セーブに触れない。

### 3.1 実セーブの控えを取る（最初に1回）

読むだけの操作なので安全。念のための控え。

```powershell
$src = "$env:APPDATA\Godot\app_userdata\GuildManager.Godot"
$bak = "D:\gm_backup\" + (Get-Date -Format 'yyyyMMdd_HHmmss')
New-Item -ItemType Directory -Force $bak | Out-Null
Copy-Item "$src\savegame.json", "$src\profile.json" $bak -ErrorAction SilentlyContinue
Get-ChildItem $bak
```

### 3.2 サンドボックスを作る／最新にする

リポジトリのルートで実行する。2回目以降も同じものを流せば最新になる
（`project.godot` も元のもので上書きされるので、名前の書き換えまで必ず一緒に流す）。
`/MIR` は宛先の余分なファイルを消すので、**`$sb` を書き換えるときは宛先を間違えない**。

```powershell
$repo = (Get-Location).Path
$sb   = 'D:\gm_sandbox'   # リポジトリの外に置く
if (-not (Test-Path "$repo\guild-manager.godot\project.godot")) { throw 'リポジトリのルートで実行してください' }

robocopy "$repo\GuildManager.Core"   "$sb\GuildManager.Core"   /MIR /XD bin obj /NFL /NDL /NJH /NP
if ($LASTEXITCODE -ge 8) { throw "コピー失敗: Core ($LASTEXITCODE)" }
robocopy "$repo\docs\04_バランス表"    "$sb\docs\04_バランス表"    /MIR /NFL /NDL /NJH /NP
if ($LASTEXITCODE -ge 8) { throw "コピー失敗: バランス表 ($LASTEXITCODE)" }
robocopy "$repo\guild-manager.godot" "$sb\guild-manager.godot" /MIR /XD .godot .godot_ai_update bin obj /NFL /NDL /NJH /NP
if ($LASTEXITCODE -ge 8) { throw "コピー失敗: godot ($LASTEXITCODE)" }

# プロジェクト名を変える（保存先のフォルダが分かれる）。BOM なしの UTF-8 で書く
$pg = "$sb\guild-manager.godot\project.godot"
$text = [IO.File]::ReadAllText($pg) -replace 'config/name="[^"]*"', 'config/name="GuildManager.Sandbox"'
[IO.File]::WriteAllText($pg, $text, (New-Object Text.UTF8Encoding $false))
if (-not (Select-String -Path $pg -Pattern 'config/name="GuildManager.Sandbox"' -Quiet)) { throw '名前の書き換えに失敗' }
'サンドボックスの準備OK'
```

- robocopy の終了コードは 0〜7 が成功、8 以上が失敗。
- コピーの相対配置（`GuildManager.Core`・`docs\04_バランス表`・`guild-manager.godot` が同じ親の下）は変えない。
  Godot 側のプロジェクトは `..\GuildManager.Core` を参照し、Core はビルドのときに `..\docs\04_バランス表` の CSV を出力へ写す。
- このスクリプトを `.ps1` に保存するなら、日本語のパスがあるので BOM 付き UTF-8 で保存する（Windows PowerShell 5.1 の場合）。

### 3.3 ビルドと取り込み

```powershell
$godot = 'D:\Godot_v4.7.2-stable_mono_win64\Godot_v4.7.2-stable_mono_win64_console.exe'   # PATH には無い
dotnet build "$sb\guild-manager.godot"
& $godot --headless --path "$sb\guild-manager.godot" --import
```

`MCP | plugin disabled in headless mode` と出るのは正常。
コマンドが別々のシェルで実行されるときは、`$sb`・`$godot` を毎回定義し直す。

### 3.4 Godot エディタと MCP（Godot AI）で動かす

このプロジェクトには MCP のプラグイン「Godot AI」（`addons/godot_ai`）が入っていて、Antigravity から
エディタの操作・ゲームの実行・ゲーム画面の撮影・クリックやキーの入力・ログの読み取りができる。
（Antigravity 側の MCP の設定はユーザーが済ませている。つながらないときは、エディタの「Godot AI」のドックで
Configure を押してもらうようユーザーに頼む。）

1. **元のプロジェクトを開いている Godot エディタがあれば、ユーザーに閉じてもらう。**
   MCP は開いているエディタにつながるので、元のプロジェクトのエディタが開いていると、そちらを操作してしまうおそれがある。
2. サンドボックスをエディタで開く：`& $godot -e --path "$sb\guild-manager.godot"`
3. MCP の `editor_state` を呼び、`project_name` が **`GuildManager.Sandbox`** であることを確かめる（§3.5）。
4. `project_run` でゲームを起動し、ゲーム画面の撮影・`game_manage`（UI要素の一覧・マウス／キー入力）・`logs_read`（エラーの確認）を使う。
   ツールの細かい引数は、各ツールの説明に従う。

### 3.5 起動の前に毎回確かめること

- MCP なら：`editor_state` の `project_name` が `GuildManager.Sandbox`。違えば**何も起動せず**ユーザーに知らせる。
- コマンドなら：`--path` が `$sb`（`D:\gm_sandbox\...`）を指している。
- 迷ったら起動しない。

### 3.6 試すときのゲームの状態

| したいこと | やり方 |
|---|---|
| 初めて遊ぶ人と同じ流れ | サンドボックスの保存先（`%APPDATA%\Godot\app_userdata\GuildManager.Sandbox\`）を空にして起動 → 手ほどき「あり」で始まる。**`GuildManager.Godot` のフォルダと取り違えない** |
| 全部のタブを初めから見る | 同じ保存先に `profile.json` を `{"ClearedOnce":true}` の内容で置く → 新しいゲームで「なし」を選ぶ |
| ユーザーの今の状態（中盤以降の画面） | 実セーブの `savegame.json` を**コピーして**サンドボックスの保存先へ置き、「続きから」 |
| お金が足りない | ⚙️ システムの「🛠 デバッグ：所持金 +10,000 G」（デバッグ版のときだけ出る） |

### 3.7 MCP を使わずに動かす（検証用のスクリプト）

まとまった操作を何度も繰り返すときや、MCP がつながらないとき：

1. サンドボックスに検証用の C#（例：`res://_verify/VerifyRunner.cs`、`Node` を継承）を作り、サンドボックスの `project.godot` の `[autoload]` に足す。
   **リポジトリ側には作らない。**
2. `dotnet build "$sb\guild-manager.godot"` → `--headless --import`
3. ロジックだけなら `& $godot --headless --path "$sb\guild-manager.godot" --quit-after 600`（数字はフレーム数）
4. **画面を撮るなら `--headless` を付けない**（headless では描画されないので真っ黒か空になる）。
   スクリプトで数フレーム待ってから `GetViewport().GetTexture().GetImage().SavePng("user://shots/名前.png")`。
   `user://` はサンドボックスの保存先。

## 4. デバッグの進め方

### 4.1 まず機械的な確認（基準を取る）

リポジトリのルートで：

```powershell
dotnet test GuildManager.Core.Tests          # 件数と失敗を記録（docs/06 の最後の項目に直近の件数がある）
dotnet build guild-manager.godot             # 警告0が決まり。警告・エラーがあれば全部記録
dotnet run --project tools/balance_sim -- campaign 3 1440   # 例外や不自然な値（NaN・桁外れ）が出ないか
```

ここまではリポジトリのファイルを変えない（`bin`・`obj`・`.godot` は git の対象外）。
**バランスの良し悪し（強すぎる・弱すぎる）は今回の対象外**。気づいたことは「範囲外で気づいたこと」に一行で。

### 4.2 コードを読んで探す観点

| 観点 | 見る所 |
|---|---|
| イベントの二重登録 | `+=` に対応する解除が無く、画面を開き直すたびに処理が二重に走る |
| 破棄したノードの参照 | `QueueFree()` の後に同じノード・小窓を触る。`Dispose()` を直接呼んでいる |
| ノードの参照 | `GetNode<T>("%Name")` の名前と `.tscn` の `unique_name_in_owner` が合っているか。深いパスで辿っていないか |
| null | `#nullable enable` の下で `!` で黙らせている所に、本当に null が来る経路が無いか |
| 画面と Core の食い違い | 画面（scripts）が自前で計算していて Core の結果と違う（決まりでは、画面は Core の関数から値を取る） |
| 文言と仕様の食い違い | ツールチップや説明文の数字・条件が、`docs/03` の仕様や `docs/04` の CSV の値と違う |
| CSV のキー | コードが読むキーが CSV に無い（起動時に例外）。備考に ASCII のカンマがあるのに `"…"` で囲んでいない |
| セーブ互換 | モデルに足した項目が `GameState.FromSaveData` で補われず、旧セーブで壊れる |
| 境界 | 所持金がマイナス・部隊が0人・全員が出撃中・選んでいた冒険者が引退や除籍で消える・年度末（48週）・満期引退・強制除籍・派遣中 |
| 自動スキップ | 「次の月へ」が止まるべき所で止まらない／止まらなくてよい所で止まる |
| 文字 | 字体に無い絵文字が □ になる（既知：🌫 は ⚠ に替えた）、文が切れる・はみ出す |

### 4.3 遊んで探す（サンドボックスで）

次の筋書きを、画面を撮りながら進める。各段でログ（`logs_read` やコンソール）に
`ERROR`・`Exception`・`NullReferenceException` が出ていないかを確かめる。**例外は1つでもバグとして報告する。**

1. **新しいゲーム（手ほどきあり）**：序章 → 新春ドラフトで2名 → 部隊を組む → 方針を付ける → 次の月へ を数か月。
   物語の小窓・手引き・月報が出る順番と、タブが開く時機が自然か
2. **新しいゲーム（手ほどきなし）**：全タブを順に開き、各画面の主な操作を一通り
   （配属・解除・リーダー・並べ替え／装備変更／鑑定・売却／研究／施設の着工／お抱え商での購入／依頼掲示板／大会の申し込み／月報の見返し／物語の記録／保存）
3. **ユーザーの今の状態（実セーブのコピーで続きから）**：全タブ・全小窓を開いて撮る。冒険者や装備が多いときの一覧の見やすさ
4. **意地悪な操作**：小窓を開いたまま Space、ボタンの連打、所持金が足りない状態での購入・着工、窓表示／最大化／フルスクリーンの切り替え、
   出撃中の冒険者の装備変更や引退

### 4.4 バグの報告に書くこと

- 再現手順（「新しいゲーム（手ほどきなし）から」「実セーブのコピーから」など出発点も）
- 期待した動き（根拠になる `docs/03` の § があれば書く）／実際の動き
- エラーログの全文、スクリーンショット
- 原因の見立て（`ファイル:行`）と、直し方の案
- 確度：**確定**（再現した・コードで経路を確かめた）／**可能性あり**（読んだだけで再現していない）。推測は推測と書く
- 直していないこと（修正モードでなければ直さない）

## 5. UI改善案の進め方

### 5.1 このゲームの画面の決まり（案はこれに合わせる）

- 論理 1920×1080。Anchor と Container で組む（固定の座標を直書きしない）。
- 文字の大きさはテーマで **本文16・補足15・見出し18** にそろえている。RichText の太字も通常の字体で出す（太字で強調しない）。
- 大きなパネルは枠の絵（`UiStyles.ApplyPanelArt`、normal・info・warn・danger）。選択中のトグルは青（`UiStyles.ApplySelectedToggleStyle`）。
- 文言はやさしい言い回し（「小窓」「お知らせ」「手引き」「次の月へ」）。カタカナ語や漢語の多い言い方は避ける。
- 計算式は画面に出さず、意味だけを書いて式はツールチップへ（§0.80）。
- 画面は Core の値を出すだけ（画面に計算を持たせない）。案が新しい数値を要するときは「Core に関数が要る」と書く。
- すでに判断して撤去したものを戻す案は出さない（例：大迷宮の右の「作戦週報」の欄・フッターの「1週進める」・ナビの「✖ 閉じる」は §0.80 で撤去）。
  戻すべき理由があるなら、その理由を添えて出す。

### 5.2 見る観点

- **初めての人**：最初の5分で「次に何をすればよいか」が分かるか
- **大事な数字が目立つか**：判断に要る値（勝てるか・足りるか・何週かかるか）がすぐ見つかるか。比べたいものが並んでいるか
- **押せる／押せない**：押せない理由が分かるか。押した結果が分かるか（お知らせ・表示の変化）
- **手数**：画面の行き来・クリックの回数が多すぎないか
- **読みやすさ**：文字の大きさ・行間・はみ出し・切れ・□・色の対比
- **色だけに頼っていないか**：色が見分けにくい人でも区別できるか（形・文字・印も添えているか）
- **一貫性**：同じものが画面ごとに違う名前・色・位置になっていないか
- **空のとき**：データが無い欄に、次にすることの案内があるか
- **多いとき**：冒険者20人以上・装備や遺物が多いときの一覧（並べ替え・たたみ・スクロール）
- **キーボード**：Space で次の月へ、採用の小窓の ↑↓・Space など、既にある操作が効くか
- **窓の大きさ**：窓表示や小さい画面で崩れないか（撮った窓の大きさを報告に書く）

### 5.3 案の見た目を試す

- サンドボックスの中でなら `.tscn`・`.cs` を書き換えて、案の見た目を作って撮ってよい（before／after）。
- **リポジトリ側には写さない。** 書き換えた内容は、報告書に「サンドボックスで変えた所」として差分か箇条書きで残す（実装する人が再現できるように）。
- 次にサンドボックスを最新にすると（§3.2）、書き換えは消える。

### 5.4 案の報告に書くこと

- 画面と場所（ノードの `%Name`・`.tscn`・`.cs`）
- 今の問題：スクリーンショットと、誰がどんな場面で困るか
- 案：配置・文言・色・大きさまで具体的に。before／after のスクリーンショットがあれば添える
- 手間（小・中・大）、Core の変更が要るか、セーブの形が変わるか
- 既知との関係（`docs/06` に同じ案があれば「既知」、近い案があれば「既知の案の補強」）
- 優先度（高・中・低）と、その理由

## 8. 修正モード（ユーザーが「直して」と言ったときだけ）

- 直すのは、**指定されたもの**だけ。1件ずつ。
- 直してよいのは、「仕様（`docs/03`）どおりに動いていないもの」と「落ちる・進めない」もの。
  **仕様を変える直し（ルール・数値・画面の構成を変える）はしない**。それは案として報告に回す。
- 作業するブランチはユーザーに確かめてから。コミット・プッシュは頼まれたときだけ。
- `CLAUDE.md` の決まりを守る。特に：
  - Core を変えたらテストを足すか直す（`dotnet test GuildManager.Core.Tests`）
  - コードで CSV のキーを足したら CSV にも足す
  - Godot 側は警告0（`dotnet build guild-manager.godot`）
  - ノードは `GetNode<T>("%Name")` を `_Ready()` でキャッシュ、破棄は `QueueFree()`
  - `.tscn` の ext_resource の id・uid・`unique_name_in_owner` を壊さない。新しい `.cs` を作ったら `.cs.uid` も一緒に
  - モデルに項目を足すなら、旧セーブでも壊れないようにし、`FromSaveData` で補う処理のテストを足す
  - 終わった作業・残った作業を `docs/06_タスクリスト.md` に記録する
- 直したら、サンドボックスを最新にして（§3.2）画面でも確かめる。テストの件数とビルドの警告数を報告する。
