## まとめ（先に読むもの）

**結論：「次の月へ」を押すだけでは勝てないので、クリックだけのゲームにはなっていない。けれども、勝ち負けを分けているのは「判断」ではなく「手入れをこなすこと」になっている。何を選んでもほとんど結果が変わらず、やるかやらないかだけが効く。これが「単調なクリック」に感じる正体。**

- 放置（方針を付けて「次の月へ」だけ）は30回とも解雇（ほとんどが6年目）。最小限（部隊の組み直しと採用だけ）でも30回ともクリアできない。
- 全部の手入れをすると30回ともクリアする（中央13年目）。ところが、採用・大会の出場者・依頼・装備の渡し先・施設の順・訓練先・潜る4人を**全部くじ引きで決めても、14年目に30回ともクリアする**（1年遅れるだけ）。
- 一方で、研究をやめると11/30しかクリアできず、施設や装備の手入れをやめると3年遅れる。必要なのは「足りたら買う」「強い品を強い子へ」という、いつも同じ答えの作業。
- 決戦は「火力 ≧ 要求火力」で必ず決まり（運が入らない）、数字も全部見え、扉前は構えで自動に決まる。構え3つのうち「標準」が常に最善で、「強気」は必ず負ける決戦に挑み（BUG-01）、「慎重」は序盤に破産へ向かう。
- 中盤からは張り合いが消える。マスターの機嫌は8割の週で上限の100、月報の3割が「目立った出来事は無かった」。

うまくいっていること：方針と月の手番で、週ごとの操作は1年13〜17回の手番にまで減った。月報の「来月への注意」から画面へ飛べる作りも良い。放置では勝てない作りなので、土台はある。

**直すべき順の上位5件**
1. BUG-01 強気の構えが、必ず負ける決戦に挑む（数値1つで直せる）
2. GD-01 決戦に「勝てる見込み」（確率）を入れて、構えを本当の賭けにする
3. GD-02 勝てない相手に黙って潜り続けるのをやめ、「来月の作戦」を選ぶ場面にする
4. GD-03 いつも同じ答えの手入れを、まとめて1回で済むようにする
5. BUG-02・BUG-03 出撃中の部隊の数値が0になる、方針の行が出撃先と違う場所を指す（判断に要る情報が見えない）

### 1.4 扉前と構え

| 構え | クリア | 決戦で負け | 強制除籍 | 重傷 | 扉前で撤退 |
|---|---|---|---|---|---|
| 標準 | 30/30・13年目 | 0 | 3 | 54 | 2275 |
| 強気 | 29/30・12年目（解雇1） | **313** | **27** | 157 | 1818 |
| 慎重 | **0/30**（破産10、残り20は30年で届かず） | 0 | 0 | 0 | 23920（うち備え不足 22102） |

- 決戦の勝ち負けは「火力 ≧ 要求火力」で必ず決まる（`GuildManager.Core/Systems/DungeonResolver.cs:89`、乱数なし）。大迷宮画面の見立ても数字で出るので、答えは前から分かっている。扉前は構えで自動に決まる。
- だから「強気」で挑む火力0.9〜1.0倍の決戦は必ず負ける（BUG-01）。「慎重」はすべてのギミックに万全の備えを求めるので、強い順の部隊ではほぼ挑めない。**標準が常に最善で、構えは選ぶものになっていない。**
- 標準でも、潜行の6割（2275回／3775回）は扉前で撤退して帰る。理由の92%は火力不足で、備え不足は1%。毎回1階から潜り直すので、待つ時間が長い。§0.68 で「悩むところを編成に集める」としたギミックの備えは、標準の構えではほとんど撤退の理由にならない。

## 2. 判断を作る修正案（ゲームの決まり）

### GD-01（優先度：高）（手間：中）決戦に「勝てる見込み」を入れて、構えを本当の賭けにする
- 今の問題：勝ち負けが火力と要求の比べ合いで必ず決まり、見立てで答えが分かる。扉前は自動。だから判断する所が無い（1.4）。
- 案：火力÷要求の比で勝率が決まる形にする。例：勝率＝1÷(1＋e^(−14×(比−1)))で、比0.9で約2割・1.0で5割・1.1で8割・1.2で9割4分（5%〜97%で止める）。
  - 構えの意味が「どこまで危ない橋を渡るか」になる。例：慎重＝勝率9割以上、標準＝6割以上、強気＝3割以上（`squad_orders.csv` の `*PowerMargin` を勝率の下限に置き換える）。
  - 調査（完全解析で火力+20%）・備えをそろえる・育てる・装備が、どれも「勝率を上げる手立て」としてはっきり効く。
  - 負けの痛み（撤退でHP20〜40%減・重傷・まれに除籍）が、そのまま賭け金になる。
- 変える所：`DungeonResolver.Resolve`（勝ち負けに乱数を1回。ほかの抽選の順を変えないよう別の乱数にする）、`SquadOrderSystem.JudgeEngage`、`squad_orders.csv`、大迷宮画面の見立て（勝率を出す）、balance_sim。
- 気をつけること：運で負けても納得できるよう、見立てと月報に勝率を必ず出す。今の標準（比1.0で必ず勝つ）からの変わり方が大きいので、曲線の位置はシミュレーターで合わせる。

### GD-02（優先度：高）（手間：中）勝てない相手に黙って潜り続けるのをやめ、「来月の作戦」を選ぶ場面にする
- 今の問題：潜行の6割が扉前で「火力不足」で撤退し、方針は何も言わずに1階から潜り直す（1.4）。放置で解雇されるのも同じ流れで、森の40Fの扉前で撤退を28回くり返すあいだ成果が出ず、機嫌が尽きる（そのあいだに名簿も引退で減っていく）。月報の3割は「目立った出来事なし」。
- 案：主力が火力不足で撤退した月は、月報の「来月への注意」の先頭に、次の作戦を2〜4択で出す（ボタンで方針を書き換える）。
  1. 迷宮調査に切り替える（完全解析まであと何週・解析後の火力と勝率）
  2. 別のフィールドの主を狙う（おまかせの候補と勝率）
  3. 鍛える月にする（全員を訓練・自主練へ。来月の見込み）
  4. このまま潜り続ける（構えと勝率）
  - 同じ相手で2回目からは1行にたたむ。止める条件（`WeekResult.ShouldStopMonth`）の「本当に決めることがあるときだけ止める」に当てはまる。
- 黙った繰り返しが「ここが勝負どころ」の場面に変わり、待つだけの時間も減る。GD-01 の勝率と組み合わせると効き目が大きい。
- 変える所：`SquadOrderSystem`（撤退の理由を部隊ごとに覚える）、`WeekResult`、`MonthlyReport`（注意の行）、`MonthlyReportPopup`（作戦のボタン）。

### GD-03（優先度：高）（手間：中）いつも同じ答えの手入れを、まとめて1回で済むようにする
- 今の問題：1年に約120回の操作のうち、鑑定・売却・着せ替え・購入・霊薬・交渉・訓練・研究の年約63回は「強い品を強い子へ」「足りたら買う」で足りる作業。大会の出場者（年約21回）も、くじ引きと結果が変わらない（1.2）。
- 案（§11「決める回数を減らし、1回の決断を重くする」の続き）。手で選びたい人の道は残す。
  - 倉庫：【まとめて鑑定】（予算を残して、金・虹以外を一度に）
  - 装備：部隊ごとの【おすすめを着せる】（上がる値を見せてから確定）
  - 売却：【いらない物をまとめて売る】（研究・霊薬・受けた依頼で使う素材は残す）
  - 大会：月のはじめの【おすすめの子で申し込む】
  - 契約交渉：システム画面で「満足度が下がったらボーナスで応える」を選べる
- 変える所：`InventoryPanel`・`EquipmentPopup`・`TournamentPanel`・`SystemPanel` と、それぞれの「おすすめ」を返す関数を Core に（画面に式を持たせない）。

### GD-04（優先度：中）（手間：小〜中）中盤から張り合いを残す（機嫌とお金）
- 今の問題：機嫌は8割の週で上限の100、お金は4年目以降の半分の週で1万G以上（1.5）。どちらも判断を迫らない。
- 案（数値は仮。シミュレーターで合わせる）：
  - 機嫌：上機嫌（80以上）の週は、新しい成果（撃破・新しい階層・依頼の達成）が無ければ少し下がる（例：−2）。いつもの採取・調査だけでは上機嫌を保てず、上機嫌の内職×1.5が「深く潜り続ける」ご褒美になる。
  - お金：取り合いになる大きな使い道を足す。例：Lv4・5の改築費を1万G級にする、上位装備の段を高くする、研究の後半を高くする。あるいは収入を少し下げる。
- 変える所：`master_mood.csv`・`MasterMoodSystem.ProcessWeeklyMood`、`facility.csv`・`equipment.csv`・`research.csv`。`docs/04_バランス表/README.md` も直す。

### GD-05（優先度：中）（手間：中〜大）選び方で結果が変わるようにする（編成・依頼・育成）
- 今の問題：選び方を全部くじ引きにしても1年しか遅れない（1.2）。
- 案：
  - 編成：即死級以外のギミックでも、備えが「一部」以下なら勝率が大きく下がる（GD-01 の勝率に備えの不足を掛ける）。ボスごとに組み替える意味が出る。
  - 依頼：報酬を「進み方を変える物」にする。例：ギミックの備えになる固有武具、施設の上限Lvを1つ開ける、出撃枠の前借り。お金と遺物は、お金が余ると効かない。
  - 育成：§11④（トレードオフ）の具体化。訓練でしか上がらない伸びしろ（PAの上限+）を作る、霊薬に副作用を持たせる（例「AGI+8・PA+5、その年は燃え尽きやすい」）。
- 変える所：`DungeonResolver`、`commissions.csv`・`CommissionSystem`、`TrainingSystem`・`elixir.csv`。

### GD-06（優先度：中）（手間：小）「判断の効き目」を物差しにして、直すたびに測る
- 案：計測の道具（`計測の道具/`）を balance_sim に `audit` モードとして入れ、「くじ引きのクリア年 − 良い決まりのクリア年」を毎回出す。今は約1年（13年のうち）。GD-01〜05 のあと、これが3年以上に広がるか、くじ引きでは負けることがあるかを見る。
- BUG-06 を先に直さないと、±1年の揺れで差が読めない。

## 3. バグ

### BUG-01（重さ：重大）（確度：確定）強気の構えが、必ず負ける決戦に挑む
- 再現手順：潜行の方針の部隊の構えを「強気」にし、火力÷要求が0.9〜1.0のボスの扉前に着く。
- 期待：強気は「火力が少し足りなくても挑む」（構えのツールチップ、`guild-manager.godot/scripts/UI/DungeonPanel.cs:250`）。少しは勝つ見込みがあるはず。
- 実際：決戦は火力 ≧ 要求でしか勝てない（`GuildManager.Core/Systems/DungeonResolver.cs:89`、乱数なし）。強気の扉前の判断は要求×0.9以上で挑む（`GuildManager.Core/Systems/SquadOrderSystem.cs:232`、`squad_orders.csv` の `BoldPowerMargin` 0.9）。比が0.9〜1.0なら必ず負け、撤退の損耗（HP20〜40%減、`dungeon.csv` の `RetreatHpLossPct*`）と重傷・古傷・除籍の抽選だけを受ける。
- 計測（30回）：決戦の負け313回、強制除籍27人（標準は3人）、重傷157（標準は54）。クリアの年は標準と変わらない。
- 直し方の案：GD-01 を入れる。すぐ直すなら `BoldPowerMargin` を1.0にし、強気は「備えとHPを問わない」だけにする（ツールチップも直す）。

### BUG-02（重さ：中）（確度：確定）出撃中の部隊を開くと、指標がすべて0になる
- 再現手順：部隊・冒険者画面で、出撃中の部隊のタブを選ぶ（shots/02）。
- 期待：今出撃している顔ぶれの走破力・討伐火力など（あるいは「出撃中のため表示しない」）。
- 実際：走破力0・討伐火力0・護衛0・隠密0・解析0・採取0・部隊健全度0%。
- 原因の見立て：`guild-manager.godot/scripts/UI/PartyFormationPanel.cs:359` が `PartyFormationSystem.BuildDispatchParty` で部隊を組み、出撃中の隊員（`IsAvailable` が偽）を外すので空の部隊になる（`GuildManager.Core/Systems/PartyFormationSystem.cs:137-150`）。
- 直し方の案：出撃中なら、その出撃（`ActiveDungeonMission.Party`）の顔ぶれで `CalculateMetrics` を呼ぶ。

### BUG-03（重さ：中）（確度：確定）方針の行の「おまかせ（今は○○）」が、出撃中の部隊の実際の行き先と違う
- 再現手順：6年目のセーブで、主力が翠緑の原生林の第51層を潜行中（左の欄「鈴隊：進軍中 第51層」）に大迷宮画面を開く（shots/01）。
- 実際：方針の行は「『主力』＝おまかせ（今は忘却の古代廃墟）で潜行を続ける（出撃中）」。
- 原因の見立て：`guild-manager.godot/scripts/UI/DungeonPanel.cs:323-325` の `OrderSummary` が、出撃中でも `SquadOrderSystem.ResolveField` を呼ぶ。出撃中は隊員が出撃できない扱いで部隊が空になり、`ResolveField` は「表示のために最も深いダンジョン」を返す（`GuildManager.Core/Systems/SquadOrderSystem.cs:133`）。
- あわせて、同じ部隊が左の欄では「鈴隊」（隊長の名前、`DungeonPanel.cs:575-576`）、方針の行では「主力」（部隊の名前）と2つの名前で出る。
- 直し方の案：出撃中は「出撃中：翠緑の原生林 第51層（帰ったら次は○○）」と出す。出撃の表示名は `SavedPartyId` から部隊の名前にそろえる。

### BUG-04（重さ：軽）（確度：確定）ヘッダーの暦に「月」が無い
- 実際：ヘッダーは「6年目 春 第5週」（季節の中の週、`guild-manager.godot/scripts/MainDashboard.cs:1881`）。月報の見出しは「6年目 春 1の月」、`GameCalendar.Format` は「春 2の月 第1週」の形。
- 根拠：§0.70 で月を1ターンにし、暦は「1年目 春 2の月 第3週」とした。
- 直し方の案：ヘッダーを `GameCalendar.Format`（または「春 2の月」＋小さく「第1週」）にする。

### BUG-05（重さ：軽）（確度：確定）深さの目盛りで、到達階の印と階層の数字が重なる
- 実際：到達階がボスの階（10の倍数）と重なると、「▶70F」と「70F」が同じ所に描かれて読めない（shots/07）。
- 原因の見立て：`guild-manager.godot/scripts/UI/DungeonDepthBar.cs:146`（ボスの階の数字）と `:178`（到達階の印）が、どちらも左の数字の欄に右寄せで描く。
- 直し方の案：到達階の印と近いボスの階の数字は描かない、または到達階の印を棒の右側に出す。

### BUG-06（重さ：中・開発）（確度：確定）同じシードでも結果がそろわない（シミュレーターの比較が±1年揺れる）
- 再現手順：`dotnet run --project tools/balance_sim -- campaign 5 1440` を2回続けて流すと、大会の出場数と撃破数の推移が毎回違う（1回目 出場 254, 230, 217…／2回目 238, 236, 211…）。
- 原因の見立て：大会の年の暦の乱数の種に、最初の部隊の Guid のハッシュを使っている（`GuildManager.Core/Systems/TournamentSystem.cs:184`）。招待大会のご褒美の固有武具の選び方も、大会の Guid のハッシュ（同 `:548`）。Guid は毎回変わる。
  - この2か所を年・月から作る種に替えると、同じ設定で2回流した結果が一致することを、写しで確かめた（リポジトリは変えていない）。
- 影響：05技術メモ §5「乱数ストリームを1本に。バグ再現・テストが安定する」に反する。シミュレーターで±1年の差を比べると読み違える（docs/06 に残っている比較にも、この揺れが入っている可能性がある）。ゲームでは、最初の部隊を消して作り直すと、翌年の大会の暦が変わる。
- 直し方の案：種をセーブにある値（年・ゲームのシードなど）から作る。

## 5. 範囲外で気づいたこと

- balance_sim は方針（`SquadOrderSystem`）を通さずに直接出撃させるので、画面の流れ（方針と月の手番）と少しずれる。計測の道具では画面どおりの流れで測った（クリアの年はほぼ同じ12〜13年目）。
- balance_sim のプレイヤーは物語の場面を見ないので、`StorySystem.MarkSeen` の副作用（エンディングのあとのルミナの加入、手引きが覚える対象）がシミュレーターでは起きない。計測の道具では、手番ごとに場面を見たことにした。
- 大会に出ない場合、balance_sim（直接出撃）では10回中8回が解雇・破産になるが、画面どおりの流れでは28/30がクリアした。違いは、行き詰まったときに調査・採取の部隊が成果を出し続けて機嫌を保つかどうか。行き詰まり → 成果なし → 機嫌の退屈減衰 → 解雇、という流れは、人が遊ぶときも起こりうる（GD-02 で知らせられる）。

## 付録：計測の方法

- 道具：`tools/balance_sim/Program.cs` の写しに、`計測の道具/Program.cs.diff` の変更と `計測の道具/Audit.cs.txt` を足したもの（使い方は `計測の道具/README.md`）。リポジトリでは組み立てない。
- 画面どおりの流れ：手番で操作する → `SquadOrderSystem.Execute` → `WeekProcessingSystem.ProcessWeek` を、月の終わりか止まる条件（`WeekResult.ShouldStopMonth`）まで1週ずつ。手番は月のはじめと、月の途中で止まったとき（`AutoSkipService.AdvanceMonth` と同じ）。
- 関わり方：L0（放置）・L1（最小限）・L2（手入れ。依頼・霊薬・秘薬は使わない）・L3（全部）。`simple` は強い順の4人＋おまかせ、付けないとボスに合わせて組む。選び方のくじ引きは `randhire` ほか、構えは `bold`・`cautious`。手入れの中身は balance_sim の campaign のプレイヤーと同じ決まり。
- 回数：各30回、最長30年（1440週）。
- 撮影：scratchpad に Core・バランス表・Godot のプロジェクトを同じ並びで写し、`config/name` を `GuildManager.Sandbox` に変え、撮影用の autoload で各画面を開いて撮った（Godot 4.7.2 Linux 版・仮想の画面・1920×1080）。6年目のセーブは計測の道具で作った（物語の場面は見たことにした）。
